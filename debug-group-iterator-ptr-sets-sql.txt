NOTE
----
This is the SQL these queries *should* compile to, hand-derived from the
project's existing IR->SQL idioms. It is NOT produced by running the compiler.
Today `compileGroupStmtToSQL` (src/sql/gel_ir_compiler.ts:696) is a stub that
only emits `SELECT <subject> AS "group_subject"`, so the top-level GROUP
statement is not actually lowered yet. The SQL below is the model to implement.

No CTEs are used -- the subject set is an inline subquery in the FROM clause,
matching the project's dominant idiom (e.g. `(SELECT ... UNION ALL ...) g0`).

Idioms reused (all already present in src/sql/gel_ir_compiler.ts):
  * Object shape  -> json_object('k', col, ...)            (compile*ShapeObjectExpr)
  * Set of objs   -> COALESCE(json_group_array(...), json('[]'))   (embedded group)
  * group output  -> json_object('key',..,'grouping',..,'elements',..)
  * FOR n in {8,9}-> (SELECT 8 AS "value" UNION ALL SELECT 9 AS "value") g0
  * free type root-> CROSS JOIN (SELECT ... FROM "cards__user") g1   (line ~150)
  * cards::User   -> table "cards__user", columns "id","name", lit "__source_type"

Each top-level group produces one result row per group; the group object lives
in the "value" column (same column the runtime collects for scalar/free selects).
Element ordering is unspecified under SQLite GROUP BY; the tests use tb.bag()
(order-independent), so no ORDER BY is required for correctness. A
`ORDER BY <rowid>` could be added for determinism, mirroring the embedded-group
lowering.

Relevant data: cards::User rows = Alice, Bob, Carol, Dave (4 users).

 1. test_edgeql_group_iterator_ptr_sets_01            (line 547)
================================================================================
EdgeQL:
    group (
        for n in { 8, 9 }
            select cards::User { name, b := n }
    ) by .name;

Subject = 4 users x 2 iterations = 8 rows {name, b}. GROUP BY name -> 4 groups,
2 elements each ({...,b:8} and {...,b:9}).

SQL:
    SELECT json_object(
        'key',      json_object('name', s."name"),
        'grouping', json_array('name'),
        'elements', COALESCE(
            json_group_array(json_object('name', s."name", 'b', s."b")),
            json('[]'))
    ) AS "value"
    FROM (
        SELECT
            g1."name"  AS "name",
            g0."value" AS "b"
        FROM (SELECT 8 AS "value" UNION ALL SELECT 9 AS "value") g0
        CROSS JOIN (
            SELECT 'cards::User' AS "__source_type", "id" AS "id", "name" AS "name"
            FROM "cards__user"
        ) g1
    ) s
    GROUP BY s."name";

================================================================================
 Implementation notes (for wiring this into compileGroupStmtToSQL)
================================================================================
1. The subject set is already compilable: when statement.subject is a
   for_expr, compileForExprSource() produces the FROM (UNION ALL + CROSS JOIN
   for the free type root). For a plain bound/aliased set it is a normal
   select source. Emit that as an inline `(...) s` subquery in the FROM,
   projecting every column referenced by either the BY atoms or the output
   shape. (No CTE needed.)

2. The BY atoms (.name / .b / .a) become the GROUP BY columns AND the
   'key' json_object pairs. 'grouping' is json_array of the distinct BY atom
   names (mirrors compileEmbeddedGroupSQL, line ~7546).

3. The output shape (default = subject's shape; or the re-projection in
   `group X { name } ...` / `group (select X {..}) ...`) drives the per-element
   json_object inside json_group_array. Note tests 5 & 7 prove the output
   shape is independent of the key: `b` stays available for the key even when
   dropped from `elements`.

4. Wrap each json_object(...) AS "value" so the runtime collects one group
   per row, exactly like scalar/free-object selects.

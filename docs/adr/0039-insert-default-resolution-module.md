# Lift INSERT default-resolution out of the write executor

`runWriteWithAccessPolicies` (the ~660-line write executor) carried a ~97-line inner closure, `applyPendingInsertDefaults`, that fills the columns an INSERT left pending because the planner couldn't lower their `default :=` to the literal/function-call IR. It handles five kinds — a literal default, a function-call default, a general SQL-evaluated default (`default := (SELECT count(T))`), a `__source__`-referencing default (substituted with the row's assigned values), and a snapshot-memoized default (one evaluation reused across a FOR loop's rows). As a closure inside the executor it was reachable only by running an INSERT; none of the five kinds had an isolated test.

**Decision (done):** add `src/runtime/default_resolution.ts` exporting `applyPendingInsertDefaults(values, deps)`. The closure body moves verbatim; the engine services it called are passed as a small **injected-deps** record rather than imported — which keeps the dependency one-directional (no `engine.ts` import cycle) and makes the function testable with fakes:

- `subjectType` / `snapshotDefaultCache` — the data it reads.
- `evalSelect(stmt) → rows | undefined` — compile + single-SQL gate + run a SELECT (wraps `getCompilerService().compile` + `resolvedRuntimeTarget` + `lowersToSingleSql` + `runGelSelectSQL`).
- `evalFunctionCall(name, args)` — evaluate a function-call default (wraps `executeFunctionCall`).
- `isResolvedSourceValue(v)` / `isPendingRewriteValue(v)` — the two pending-sentinel checks; the engine owns the canonical sentinel strings, so no sentinel literal is duplicated in the new module.

`parseEdgeQL`, `tryResult`, `AppError` are imported from their own modules; `substituteSourceRefs` (the pure `__source__`→literal AST walk) and the `tryResult({captureAll})` wrapping stay in the module, so a parse error, an unresolved-`__source__` throw, or an `evalSelect` failure all still leave the column pending. `engine.ts` drops 85 lines; the call site passes the deps closures (capturing `db`/`schema`/`context`).

**Verification.** Behaviour-neutral by construction — the dispatch, substitution, memoization, and error-swallowing are unchanged; only the engine services are reached through injected closures that reproduce the original calls exactly. The write-path slice (`insert`/`for`/`delete`/`triggers`, 435 tests) ran `87–88 failed` across runs; the stashed baseline was `88`, and the *same* post-change code produced `87` then `88` on consecutive runs (and `edgeql_insert` alone is a stable `53`) — the ±1 is the suite's documented order-flakiness, not a regression. `tsc` clean, lint clean. New test surface: `tests/default_resolution.test.ts` (9 unit tests) drives each kind with fake deps — literal, function-call, SQL-evaluated, can't-lower-stays-pending, snapshot reuse + memo-write, skip-already-set, rewrite-sentinel re-resolution, and `__source__`-unresolved-stays-pending — none of which previously had isolated coverage.

**Consequences.** INSERT default resolution is a module with a small injected-deps interface and a real test surface; the write executor shrinks toward its orchestration role (continuing ADR 0037's "executor over seams" shape). A new default kind is added and tested in `default_resolution.ts` without running an INSERT.

**Why record it:** the deps record (three injected functions) is wider than a pure-data extraction would be. That is deliberate: `applyPendingInsertDefaults` genuinely needs the compiler service, the SQL read path, and function-call evaluation — all engine-internal. Injecting them (rather than importing) is what keeps `engine.ts → default_resolution.ts` one-directional and the function unit-testable; a future reader should not "simplify" it by importing those services back (that reintroduces the cycle and re-buries the test surface).

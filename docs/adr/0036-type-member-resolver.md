# Extract the inheritance/overload member resolver from the uiSchema megafunction

`typeDefsFromDeclarative` (`uiSchema.ts`) was a ~395-line function whose hardest sub-problem — resolving a type's full member list by folding in inherited members and merging `overloaded` re-declarations — lived as a nested `resolveMembers` closure plus a cache and three helper closures (`isSubtypeOf`, `cloneMemberForInheritance`, `inheritMemberAnnotations`), supported by five module-level helpers (`cloneMember`, `validateMemberAnnotations`, `assertOverloadCompatibility`, `mergeOverloadedMember`, and the `cloneConstraint`/`cloneConstraints`/`mergeConstraintSets` trio). The resolution carries sharp invariants — first-seen-wins on inherited names, overload-kind/scalar/cardinality compatibility, link-property merge, a recursion cycle guard — yet was reachable only by converting a whole `DeclarativeSchema`, so none of it had an isolated test surface.

**Decision (done):** add `src/schema/type_member_resolver.ts` with a `TypeMemberResolver` class. It is constructed once per schema with `(types, annotationRegistry)`, builds its own `typeByName` index and resolved-member cache, and exposes a single method — `resolveMembers(typeDecl)`. The three resolution closures become private methods; the five supporting helpers move with it as module-level functions. `cloneConstraints` is the one helper still needed by `uiSchema.ts`'s mapping loop, so it is exported from the new module and imported back — keeping the dependency one-directional (`uiSchema → type_member_resolver`, no cycle). `typeDefsFromDeclarative` now constructs `const memberResolver = new TypeMemberResolver(schema.types, annotationRegistry)` and calls `memberResolver.resolveMembers(typeDecl)`; `uiSchema.ts` drops 308 lines.

**Verification.** Behaviour-neutral by construction: every helper moved verbatim, and the three closures became methods with identical bodies (the only mechanical change is `isSubtypeOf` passed to `assertOverloadCompatibility` as an arrow that re-binds `this`). The inheritance/overload/link-prop slice (`linkprops`/`select`/`linkatoms`/`advtypes`/`insert`/`userddl`/`dump01`, 973 tests) ran `258–259 failed` across runs; the stashed baseline was `259`, and the *same* post-change code produced `258` then `259` on two consecutive runs — the ±1 is the suite's documented order-flakiness (the `select` suite alone fails 89, vs 81–82 inside the combined set: the count is composition-dependent), not a regression. `tsc` clean, lint clean. New test surface: `tests/type_member_resolver.test.ts` (5 unit tests) drives the resolver off the real `issues` schema — multi-base inheritance fold + ordering, overloaded-property constraint merge with de-dup, overloaded-link property merge (`since` added, base `note` preserved), and the deep-clone/cache-isolation contract.

**Consequences.** The inheritance + overload merge rules have one home with a small interface and a real test surface. A change to how members inherit or overloads merge happens in `TypeMemberResolver`, guarded by its unit tests, instead of inside a 395-line conversion function. `typeDefsFromDeclarative` shrinks to its actual job: mapping resolved members onto `TypeDef` fields/links/computeds.

**Why record it:** a future reader will see `cloneConstraints` exported from `type_member_resolver.ts` yet consumed by `uiSchema.ts`, and may want to "tidy" it into a shared util. It lives with the resolver because the resolver owns the constraint-clone/merge rules; the single back-import is deliberate, to keep the dependency edge one-directional and avoid an import cycle.

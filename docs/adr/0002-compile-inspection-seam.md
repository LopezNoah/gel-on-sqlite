# Establish a compile-inspection seam; report the honest SQL gate, defer the strategy classifier

The compile interfaces (`compileASTToGelIR`, `compileGelIRToSQL`, `CompilerService.compile`) are **deep** — a small interface over a lot of behaviour — but nothing crossed them as a test surface. Every test asserted executed result rows, so a lowering bug surfaced only as a wrong row, un-localised to the layer that broke; ~28 gitignored root runners (`qast`/`qir`/`qsql`/…) each re-derived the `parse → expand → compile → dump` boilerplate by hand as informal probes (architecture review candidate #1).

**Decision (done):** Add `src/compiler/inspect.ts` — a **Compile inspection** seam that runs parse → Live IR → SQL artifact *without executing against SQLite* and projects a stable set of **Compile facts** plus **Canonical SQL**. It is purely additive over `CompilerService` (no production-path change, no `engine.ts` edit). Two adapters cross the seam — golden tests (`tests/inspect.test.ts`) and a dev CLI (`bin/inspect.ts`) — which is what makes it a real seam rather than indirection; the CLI subsumes the ad-hoc runners. `inspect(schema, query)` returns a result that never throws on a query problem (parse/compile failures are captured as `{ ok:false, error }`, so "this query rejects with code X" is itself an assertable fact, and the parsed `ast` survives a compile error for tooling). `inspectorFor(schema)` binds the schema once — no hidden process-global default schema (rejected: it makes a wrong-schema mismatch look like a query bug and risks test-to-test schema leakage).

**Decision (deferred, with reason):** Compile inspection reports the **honest, artifact-derived** fact `lowersToSingleSql` (= `loweringMode === "single_statement" && sql.length > 0`) — the engine's SQL gate verbatim — and **not** a 3-way `sql | runtime | reject` strategy. Two alternatives were rejected:

- **Approximate a `strategy` field from `loweringMode` alone** — it lies. A free-object `SELECT { a := 1, b := {2,3,4} }` lowers to `single_statement` SQL (verified), while an unsupported GROUP also produces an empty/fallback artifact; `loweringMode` cannot distinguish *runtime* from *reject*, so a `strategy` field derived from it would mislabel real cases. A test surface that lies is worse than none.
- **Replicate the engine's decision into the inspector** — it rots. The true decision is two facts the engine encodes in two places: the `loweringMode !== "single_statement" || sql.length === 0` gate (repeated ~15×) and the `needsRuntimeEval`/`bindingNeedsRuntime` AST walk (`engine.ts:1878–2031`). Copying that walk into `inspect.ts` creates a second source of truth that drifts from the engine — the same coupling rot ADR 0001 warns about — and pulls engine-internal AST handling into a tooling module.

The accurate 3-way strategy belongs to the **lowering-strategy candidate** (architecture review candidate #2): extract `classifyExecutionStrategy(ast, artifact)` once, have the engine's ~15 gate sites and Compile inspection both consume it. At that point a `strategy` Compile fact is added, sourced from the one classifier.

**Consequences.** `inspect.ts` stays additive and every fact it reports is true. `lowersToSingleSql` is exactly the boolean candidate #2's refactor risks changing, so the golden tests are the regression net that makes candidate #2 safe to attempt — build the net first, then unify the predicate. When the classifier lands, add the `strategy` fact and re-point any golden that wants the 3-way answer.

**Why record it:** a future reader will see `inspect.ts` compute the SQL gate but no `strategy`, and will be tempted to "complete" it by copying `needsRuntimeEval` from the engine. That is the rot this ADR forbids — the strategy classifier is candidate #2's single source of truth, not the inspector's to duplicate. The seam was added with a clean type-check and 10 passing golden tests, 0 changes to existing files.

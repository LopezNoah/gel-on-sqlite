# Unify the SQL-gate predicate (partial candidate #2)

The architecture review's candidate #2 found that "can this query run as exactly one SQL statement, or must the runtime evaluator handle it?" had no single home: the predicate `loweringMode !== "single_statement" || sql.length === 0` (and its positive form) was copy-pasted across `src/runtime/engine.ts` — 17 gate sites — and a separate `needsRuntimeEval`/`bindingNeedsRuntime` AST walk (`engine.ts:1878–2031`) answered a related question a third way. Changing the rule meant finding every copy.

**Decision (done):** Extract the SQL gate as one exported function — `lowersToSingleSql(artifact)` in `src/sql/compiler_types.ts` (the home of `GelIRSQLArtifact`, a leaf module both sides already depend on, so no import cycle). The engine's 17 gate sites now call it; the Compile inspection seam (`src/compiler/inspect.ts`) computes its `lowersToSingleSql` fact through the same function. One definition, two consumers. The substitution is provably behaviour-preserving — `lowersToSingleSql` is `loweringMode === "single_statement" && sql.length > 0` and each replaced site was that boolean or its negation. Verified: a 9-file behavioural sample across the gate-heavy suites (select / group / for / insert / coalesce / functions / expressions / sql_dml) was identical before and after — `611 failed | 1369 passed | 107 skipped` both runs (the failures are the pre-existing partial-conformance baseline, not regressions); 0 type errors; the 13 compile-inspection goldens stayed green.

**Decision (scoped out, deliberately):**

- **Two `select_free` checks left untouched** (`engine.ts` ~6665, ~7745): they test `loweringMode !== "single_statement"` *without* the `sql.length === 0` clause — a genuinely different predicate. Folding them into `lowersToSingleSql` would change behaviour for an empty-SQL single-statement artifact, so they stay as-is.
- **The 3-way strategy classifier is NOT built here.** Distinguishing *runtime* from *reject* among the not-single-SQL cases requires the engine's `needsRuntimeEval`/`bindingNeedsRuntime` AST walk, which is tightly coupled to engine-internal AST handling. Extracting `classifyExecutionStrategy(ast, artifact) → sql | runtime | reject` and having both the engine and the inspector consume it remains the next step. Until then the inspector reports the honest SQL gate only, and adds a `strategy` fact when the classifier is extracted (continues `docs/adr/0002`).

**Consequences.** The "~15× duplicated predicate" the review flagged is gone — the SQL gate has one definition. The engine and the compile-inspection seam can no longer disagree about what "lowers to SQL" means. The remaining work (the 3-way classifier extracting `needsRuntimeEval`) is a larger, separately-verifiable change and is the true completion of candidate #2.

**Why record it:** a future reader will see `lowersToSingleSql` shared but `needsRuntimeEval` still private to the engine, and the two `select_free` checks still inlined, and may assume the dedup was missed. It was intentional — the gate is unified; the strategy classifier and those two distinct-predicate sites are deferred with reason.

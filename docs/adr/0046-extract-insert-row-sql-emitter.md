# Extract the write-time INSERT row SQL emitter; the rest of the write path stays procedural

A round-7 review candidate ("Split the DML write executor") proposed extracting a DML→SQL **emitter** from `runWriteWithAccessPolicies` (~578 lines), mirroring what `gel_ir_compiler.ts` does for SELECT, leaving a thin procedural driver.

**The grand framing is overstated.** Reading the write path:

- **UPDATE and DELETE already compile to SQL** ahead of time — the DML IR is lowered to `sqlArtifact.sql` by `compiler/dml_lowering.ts` + the SQL compiler. `runWriteWithAccessPolicies` simply runs that pre-built string (`db.prepare(sqlArtifact.sql).run(...)`). There is nothing to extract for them; the emitter the report imagined already exists.
- The bulk of the function is **irreducible mutation mechanics**: access-policy enforcement, `UNLESS CONFLICT` (pre-checks, ELSE-UPDATE, savepoints), per-row sequence allocation, `applyPendingInsertDefaults`, link-table and multi-scalar writes, `onTargetDelete` cascades. The same conclusion `docs/adr/0037` already reached — the function's size is mutation mechanics, not a hidden compiler.
- **INSERT is the exception, and not in the way the report meant.** Its SQL can't be compiled ahead of time because the final column set is unknown until defaults, sequences, and inline-link targets resolve *at write time*. So the INSERT row SQL is built inside the executor — but that build step *is* pure: column→value `entries` in, `{ sql, params }` out.

**Decision (done):** extract exactly that pure step into `src/runtime/dml_sql.ts` as `buildInsertRowSql(table, entries, insertColumns, pos)`. It depends only on `quoteIdent` (imported from `codegen/sql.ts` — byte-identical to the engine's local copy, so SQL output is unchanged), `PENDING_INSERT_SQL_EXPR_VALUE` (from `dml_lowering.ts`), and `AppError`. It handles the three INSERT shapes the inline code did: `DEFAULT VALUES` (no columns), positional `?` params (with boolean→1/0 coercion), and splicing a planner-deferred column's compiled SQL expression + its param slice. The caller keeps the `normalizedEntries` filter (it uses the engine-local `PENDING_INLINE_LINK_VALUE`/`PENDING_INSERT_REWRITE_VALUE` sentinels) and its own `sqlExprByColumn` map for the separate `UNLESS CONFLICT` resolved-value probe. Pinned by `tests/dml_sql.test.ts`.

**Scoped out, deliberately — the boundary.** No "DML compiler" mirroring `gel_ir_compiler`: UPDATE/DELETE need none (already lowered), and the rest of `runWriteWithAccessPolicies` resolves values *at write time* (sequences are per-row UPSERTs, defaults may run SELECTs, link targets come from subqueries/nested inserts, sibling defaults need the row to exist) — that is genuinely procedural, not emission waiting to be lifted. The link-table writers (`writeLinkTableRows`, `applyInsert/UpdateLinkAssignments`) interleave SQL building with execution and per-row logic; they are not pure emitters and are left in place.

**Verification.** `tsc` clean. Byte-identical SQL (the builder reproduces the inline strings exactly; `quoteIdent` equivalence checked). Full suite diffed against baseline: failing-set total unchanged but for the documented-flaky `test_edgeql_functions_inline_insert_iterator_03` (`docs/adr/0044`), not a regression. New unit surface covers the four INSERT shapes plus the missing-compiled-column error.

**Why record it:** a future reviewer will see `runWriteWithAccessPolicies` still ~575 lines and may re-propose the big "extract the DML emitter" split. Record that UPDATE/DELETE already compile to SQL, INSERT's SQL is write-time *by necessity* (and its pure piece is now `buildInsertRowSql`), and the remainder is mutation mechanics — sequences/defaults/links/policies resolve at write time and cannot be precompiled. `runtime/dml_sql.ts` is the home for any *further* write-time DML SQL emission, should more pure pieces appear.

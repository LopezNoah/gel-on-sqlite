# One semantic registry for the standard library

The standard library was described in **four** places that had to be hand-kept in sync:

- **metadata** (arity, volatility, `returnOptional`, `paramSetOf`) — the `DEFINITIONS` array in `src/stdlib/functions.ts`, read by name resolution and the inference passes;
- **SQL lowering** — the `STDLIB_SQL_TEMPLATES` map in `src/sql/stdlib_lowering.ts`, read by the SQL compiler;
- **runtime evaluation** — a ~500-line `switch (name)` in `executeStdlibFunction` (`stdlib/functions.ts`), read by the Runtime evaluator;
- **a name-set gate** — `BASE_SQL_NATIVE_STDLIB_LOWERING` in `src/runtime/target.ts`, an allow-list of which functions lower to SQL.

Adding or changing a function meant editing up to four lists, and they had already drifted: the `target.ts` gate had fallen behind the template map, so a fourth-and-a-half list — `UNREGISTERED_BUT_SUPPORTED` in `stdlib_lowering.ts` — was bolted on to re-admit the ~9 functions (`datetime_get`, `re_*`, `cal::time_get`, …) the gate forgot but the templates supported. Nothing forced the SQL adapter and the runtime adapter for a given function to agree they even referred to the same function.

**Decision (done):** the standard library has one home — `src/stdlib/registry.ts`. Each function is one `StdlibFunctionEntry { name, meta?, sql?, runtime? }`, co-locating its three adapters. Slots are independent: a function may have any combination (e.g. `math::sqrt` is sql-only, `math::mean` is meta+runtime-only, `std::str_upper` has all three). The registry is the single source the other modules read through:

- `stdlib/functions.ts` → a thin facade re-exporting `resolveStdlibFunction` / `tryResolveStdlibFunction` / `executeStdlibFunction` and the types, so `runtime/engine.ts`, `runtime/default_resolution.ts`, and `compiler/inference.ts` keep their import path unchanged;
- `sql/stdlib_lowering.ts` → `lowerStdlibFunctionSql` / `canLowerStdlibFunctionSql` now read the registry's `sql` slot;
- `runtime/target.ts` → `BASE_SQL_NATIVE_STDLIB_LOWERING`, `RuntimeTargetCapabilities`, `targetCapabilities`, and `canLowerStdlibFunctionToSql` are **deleted**, and `UNREGISTERED_BUT_SUPPORTED` with them. A function lowers to SQL **iff it has a `sql` slot** — the gate and the implementation can no longer disagree because they are the same fact.

`resolveStdlibFunction` still returns the historical `StdlibFunctionDef` shape (`{ name, minArgs, maxArgs, … }`) and arity-gates exactly as before; only entries with a `meta` slot resolve, so the sql-only functions remain non-resolvable (matching the old behaviour, where they had no `DEFINITIONS` entry). The `RuntimeTarget` parameter is kept on the lowering predicate: both supported targets (`sqlite`, `d1`) currently expose the same SQL-lowerable set, so lowerability is target-independent today, but the seam stays target-shaped for when that diverges. The unrelated target machinery — `assertTargetSqlCompatibility` and `D1_ALLOWED_SQLITE_FUNCTIONS` (which validates *generated* SQL against a target's allowed SQLite builtins) — is untouched.

**Scoped out, deliberately — operators stay split (the boundary):** the round-7 review also flagged the binary/unary **operators** (`+ - * / // % ++ ?? = != ?= like` …) as encoded twice — a `switch` in the Runtime evaluator's `evalExpr` versus `normalizeOperator` / `operatorToInfixSql` / `likeOperatorSql` in `gel_ir_compiler.ts`. They are **not** unified here, and this is not an oversight. Unlike the stdlib functions — where the two adapters compute the same value by different means and share metadata — the operator lowerings are *genuinely different expressions of different semantics*: the SQL side must encode three-valued logic, JSON-wrap boolean results, and `COALESCE` empty-sets in CASE expressions; the runtime side walks JS arrays with longest-common-prefix / co-iteration. There is no shared metadata to factor and no single rule expressed twice — forcing both behind one entry would just park two unrelated lambdas side by side. (Same reasoning as `docs/adr/0024`/`0025` for the deliberately-separate computed-expr parsers and tokenizers.) The three SQL-side operator helpers are a within-SQL consolidation — one engine, not SQL-vs-runtime duplication — and remain a separate concern.

**Verification.** `tsc` clean. New unit surface `tests/stdlib_registry.test.ts` pins the unification: slot well-formedness, arity gating, runtime dispatch (including the shared `range_unpack`/`array_unpack` body and the sql-only / unknown ⇒ `undefined` cases), and that the SQL-lowerable set equals the historical `BASE_SQL_NATIVE_STDLIB_LOWERING ∪ UNREGISTERED_BUT_SUPPORTED` (so the merge neither dropped nor admitted a function). Full suite (≈4,075 cases) diffed against the pre-change baseline: the failing set changed by exactly one test — `test_edgeql_functions_inline_insert_iterator_03` — confirmed pre-existing flakiness (it fails ~3-of-4 isolated runs on the unmodified baseline and ~1-of-3 with this change), not a regression. No tests fixed, none newly broken.

**Consequences.** A stdlib function is described once; adding one is a single entry. The SQL and runtime adapters can no longer drift in which functions exist, and SQL-lowerability is derived from the implementation rather than a shadow allow-list. Three lists (`DEFINITIONS`, `BASE_SQL_NATIVE_STDLIB_LOWERING`, `UNREGISTERED_BUT_SUPPORTED`) collapsed into the registry's slots.

**Why record it:** a future reviewer will see operators still implemented twice and may re-propose unifying them with the functions. That was considered and declined — the operator SQL/runtime lowerings are different semantic expressions, not a hand-synced duplicate table (see the boundary above). The merge is intentionally function-scoped.

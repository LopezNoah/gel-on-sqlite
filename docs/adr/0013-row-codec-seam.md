# A home for SQLite-row → EdgeQL-value decoding (and why the JSON catch stays)

The round-3 review's candidate #5 found that "turn a Gel-SQL result row into an EdgeQL value" lived inline in `runtime/engine.ts` as two coupled functions — `materializeGelSQLRows` (scalar-vs-object row shaping, internal-column dropping, all-null→null) and `normalizeGelSQLValue` (per-column JSON decode) — reachable only by asserting executed rows. The decode of the SQL read path had no home and no test surface.

**Decision (done):** Extract both functions verbatim into `src/runtime/row_codec.ts` and import them back into `engine.ts` (the sole caller, `runGelSelectSQL`). They are pure (no `db`/`schema`/engine-state deps), so the move is mechanical. The module is pinned by `tests/row_codec.test.ts` (9 unit tests) covering scalar sets, the `scalarResultIsStr` verbatim/unwrap rule, object-set internal-column dropping, all-null→null, and the JSON-decode fallback. The decode is now a real test surface — the win ADR 0007 (result_clauses) and ADR 0002 (inspect) established for other layers.

**Decision (rejected, with reason):** the review speculated the silent `try { JSON.parse } catch { return raw }` in `normalizeGelSQLValue` "hides bugs" and should be made loud. Closer inspection refutes that: `normalizeGelSQLValue` is **type-blind** — it does not know a column's declared type, so it guesses "string that looks like a JSON literal/container → parse it". A `str` value that merely starts with `[`/`{` (e.g. `"[draft]"`, `"{tbd}"`) fails the parse and **must** fall back to the raw string. The catch is therefore **load-bearing and correct**, not a swallowed defect — a parse failure here is an expected non-JSON string, not corrupt data. Making it throw would corrupt legitimate `str` values. (This is the opposite of ADR 0012's SQL-precompute probe, where the swallowed thing genuinely was a defect and now propagates — the two catches look alike but differ in whether failure is expected.) A unit test pins the fallback so it isn't "tightened" into a bug later.

**Decision (scoped out, deliberately):** `readRuntimeTypedAliasSourceRows` (which reads raw source-table rows and tags them with `__source_type` for the Runtime evaluator's own select path) is **not** folded in — it is a different concern (reading source rows to feed the interpreter, not decoding a finished SQL result), with different inputs and outputs. Only the SQL-result decode moved.

**Verification.** Behaviour-neutral: the decode-exercising slice (`select` / `advtypes` / `linkprops` / `coalesce` / `expressions`, 1011 tests) ran `393 failed / 615 passed / 3 skipped` both before and after — the failures are the pre-existing partial-conformance baseline; zero new failures. The functions were moved character-for-character (only their home changed), so equivalence is by construction. 0 type errors. 9 new unit tests green.

**Consequences.** The SQL-result decode has one home and a test surface. A future change to how stored JSON/scalars are decoded happens in `row_codec.ts`, guarded by its unit tests, rather than buried mid-`engine.ts`. The type-blind decode's limitation (a `str` that is valid JSON, like `"[1,2]"`, is mis-parsed to an array) is now visible and documented in one place — a candidate for a future type-aware decode, but out of scope here (it would need the result's static type threaded through, a behaviour change).

**Why record it:** a future reader will see `row_codec.ts`'s JSON `catch` and, primed by the review notes, may try to make it throw "to surface bugs". That is wrong here — the catch handles type-blind decode of legitimate non-JSON strings; only ADR 0012's probe catch hid defects. The distinction is recorded so the load-bearing fallback survives.

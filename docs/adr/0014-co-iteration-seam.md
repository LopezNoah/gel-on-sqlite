# Extract co-iteration detection from the runtime evaluator (defer the full evalExpr move)

The round-3 review's candidate #4 wanted a test seam for the Runtime evaluator's core — `evalExpr`, a ~1,300-line recursive closure inside `tryRuntimeSelectExprEvaluationAst` reachable only by executing full queries. A wholesale extraction of that closure is high-risk: the evaluator is partial-conformance, so a behaviour change surfaces as a wrong row, not a type error, and the closure captures `db`/`schema`/`context` plus several sibling helpers. The review itself flagged the safe first step — the **co-iteration logic duplicated across the `math` and `compare` cases** — as the "GOOD SEAM". This ADR takes that step and defers the rest.

**Decision (done):** Add `src/runtime/co_iteration.ts` with two pure functions:

- `findBindingRoot(expr)` — the root WITH-binding name an operand walks (`x` / `x.a` / `<int64>x[0]` → `"x"`), following `field_access` / `index_access` / `cast` wrappers. It was defined **identically** inside both the `math` and `compare` cases.
- `coIteratedBinding(left, right, env)` — the shared *detection*: when both operands walk the same binding and it is bound to a set (array) in `env`, return `{ root, rows }` so the caller iterates the operands in lockstep (`WITH x := {1,2,3} SELECT x * x` ⇒ {1,4,9}, not the 9-element Cartesian product); `null` otherwise.

The `math` and `compare` cases now call `coIteratedBinding` and keep only their genuinely-different per-row bodies — `math` binds the scalar `row` and applies the operator; `compare` binds `[row]` and runs the LCP `?=`/`?!=` comparison. Pinned by `tests/co_iteration.test.ts` (9 unit tests): wrapper-walking, same/different roots, non-set binding, absent binding, non-binding operand.

**Decision (deferred, with reason):** the **full `evalExpr` extraction is not done.** Moving the ~1,300-line closure into its own module would require threading `db`/`schema`/`context`/`env` plus the sibling helpers (`evalFilter`, `materializeShapeOnRow`, `resolveBacklinks`) through an explicit interface, on a partial-conformance evaluator where a subtle change is a silently-wrong row. That is its own behaviour-gated effort, not a mechanical move — the same reasoning ADR 0007 used to extract the safe dedup/slice helpers while leaving the four ORDER BY comparators in place. The co-iteration detection is the identical, low-risk piece; it is extracted now, and the broader evaluator-as-module remains the larger follow-up.

**Verification.** Behaviour-neutral: the co-iteration-exercising slice (`expressions` / `coalesce` / `scope` / `select`, 1025 tests) ran `393 failed / 629 passed / 3 skipped` both before and after — the failures are the pre-existing partial-conformance baseline; zero new failures. `findBindingRoot` moved verbatim and `coIteratedBinding` is exactly the detection both cases performed (`leftRoot === rightRoot && env.has(root) && Array.isArray(bound)`), so equivalence is by construction — the `compare` case's `bound.length > 0` guard is preserved as `coBinding.rows.length > 0`. 0 type errors. 9 new unit tests green.

**Consequences.** EdgeQL co-iteration detection has one home and a test surface; the `math` and `compare` cases can no longer drift in how they decide to iterate in lockstep. The first slice of "make the runtime evaluator testable" exists; the rest of `evalExpr` is unblocked but explicitly out of scope here.

**Why record it:** a future reader will find `co_iteration.ts` used by only two evaluator cases and `evalExpr` still a large closure, and may think the seam was abandoned half-done. It was scoped deliberately — the co-iteration detection is the identical, safe piece; the full evaluator extraction is a larger behaviour-gated change, not folded in silently.

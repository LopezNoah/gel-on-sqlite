# Live-IR cardinality inference (statement-level parity with the oracle)

Continuing candidate 6 (bring the Live IR to inference parity so the `semantic.ts` oracle can be retired — ADR 0001). After volatility (ADR 0015), this ports **cardinality**.

**The gap (measured).** A probe (the oracle's `edgeql_ir_card_inference.test.ts` adapted to read the Live IR's top-level `.cardinality` via `compileASTToGelIR`) passed only **22/176**: the Live IR hardcoded `defaultCardinality`. The 176 cases split into 121 **statement-level** assertions (`expectCardinality`, reading the statement's inferred cardinality) and 48 **shape-element** assertions (`expectShapeFieldCardinality`, reading `shape[].cardinality` produced by the SQL builder).

**Decision (done):** Extend `src/compiler/inference.ts` with `inferStatementCardinality(statement, schema, activeModule)`, a faithful port of the oracle's cardinality engine — `inferAstCardinality` (the full expression switch) plus the lattice helpers (`cartesianCard` / `cartesianMany` / `unionCard` / `cardUnionOfFields` / `cardIntersectOfFields`), the schema walkers (field/link/computed cardinality, object-type resolution, assignability), the **filter-exclusivity** detection (a `FILTER` that pins an exclusive single property — or all members of a compound `exclusive on (.a, .b)` — to one row yields `at_most_one`), the aggregating-function tables, and the statement-level derivation across `select` / `select_expr` / `select_free` / `insert` / `update` / `delete` / `for` (with WITH bindings in scope). `compileASTToGelIR` sets `Statement.cardinality` from it, inside the same guarded `try/catch` as volatility.

Result: **all 121 statement-level cases reach parity** (probe 22 → 143/176). A focused `tests/edgeql_ir_card_live.test.ts` (24 representative cases — object→many, exclusive/compound-exclusive filters→at_most_one, OR→many, LIMIT 1, literals, set literals, `array_agg`, arithmetic, coalesce, tuples, free objects, FOR, optional/aggregate functions) locks the capability in.

**Why this is safe (additive + guarded).** Execution reads only **per-element / per-`Set`** cardinality (`element.cardinality` / `shape.cardinality`); the **statement-level** `Statement.cardinality` is read 0× by the SQL lowering and runtime (verified). So setting it cannot change any query result. The call is `try/catch`-guarded (a pathological AST keeps the default rather than breaking a compile). Confirmed: the cardinality-exercising slice (`select` / `insert` / `functions` / `expressions` / `group`) went `508 failed / 1098 passed` → `507 / 1099` — one *fewer* failure (within ±1 order-flakiness), zero new. 0 type errors. The oracle's `edgeql_ir_card_inference.test.ts` is untouched and still 176-pass.

**Decision (scoped out, with reason):** the **33 shape-element cases** the probe still fails read the Live IR's per-`Set` cardinality, which the **SQL builder** populates — a different concern from this inference module, and one that *is* read by execution (so not additive). They were failing before this change and are unchanged by it. Reaching them is a builder task (and a behaviour-affecting one), tracked separately; it does not block statement-level cardinality parity.

**Consequences.** Statement-level cardinality now matches the oracle on the Live IR. Two of five inference dimensions (volatility, cardinality) are ported into `inference.ts`; multiplicity, type, and scope-tree remain before `semantic.ts` can be deleted. Multiplicity inference reuses cardinality, so it is the natural next step.

**Why record it:** a future reader will find cardinality computed in **both** `inference.ts` (statement-level, for the Live IR) and `semantic.ts` (the oracle), and per-element cardinality in the SQL builder — three sites. They are not redundant yet: the oracle is still the reference for the four un-ported dimensions, the builder owns shape-element cardinality (the 33 scoped-out cases), and `inference.ts` owns statement-level. The duplication collapses when the oracle is deleted (ADR 0001).

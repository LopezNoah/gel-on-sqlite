# Route the backlink read path's link-storage dispatch through the canonical helpers

The round-4 review's candidate #5 flagged that two backlink resolvers in `runtime/engine.ts` — `resolveBacklinkRowsForSubject` (the interpreter's `backlink_path` case) and `collectBacklinkSourceRows` (the GROUP backlink-shape path) — "re-derive the same link-storage dispatch." Investigation found the duplication is real but wider than those two functions, and that the two functions themselves are **not** a clean merge.

**What is actually duplicated.** Two rules, each with an existing canonical home, were re-derived inline across the engine's backlink / link-read paths:

- **The storage decision** — "is this link junction-table-backed (multi or link-properties) or inline-`<name>_id`-FK?" — the predicate ADR 0008 consolidated into `usesLinkTable`. The live pipeline still had five inline copies (`linkDef.link.multi || (linkDef.link.properties?.length ?? 0) > 0`, the `Boolean(...)`-wrapped form, and the `linkDef`/`link` variants) at `engine.ts` 1930, 2460, 8913, 9141, 11449.
- **The junction-table name** — `${tableNameForType(ownerQualifiedName)}__${link.name.toLowerCase()}` — which already exists as `linkTableName(parentQualifiedName, link)` in `codegen/sql.ts` (exported via `index.ts`). The engine re-spelled the formula at five owner-walk sites (1932, 2465, 8917, 8965, 9143), twice via a throwaway `ownerTable` local.

**Decision (done):** route all ten sites through the canonical helpers — `usesLinkTable(link)` for the storage decision, `linkTableName(qualifiedTypeName(owner), link)` for the junction-table name (dropping the two now-redundant `ownerTable` locals). `usesLinkTable` was already imported into `engine.ts`; `linkTableName` is now imported from `codegen/sql.ts`. The substitution is provably byte-identical: `linkTableName(qn, link)` is exactly `tableNameForType(qn) + "__" + link.name.toLowerCase()`, and `usesLinkTable` is the same truthiness as the inline `multi || properties.length > 0` forms (an `||` boolean context, per ADR 0008).

**Decision (scoped out, deliberately):**

- The **two backlink-resolver functions are NOT merged into one walk** (the candidate's sketch). They share the storage-dispatch primitive but differ in everything around it: `resolveBacklinkRowsForSubject` scans *every* type that declares the link (`listTypes` + `findRuntimeLinkDef`), expands each to its concrete subtypes, merges link-row columns and `@property` link-properties (`SELECT s.*, j.*`), and dedupes by concrete `(type, id)`; `collectBacklinkSourceRows` requires a `sourceType`, iterates *its* concrete closure directly, selects `s.*` only (no link-properties), and does not dedupe. Their return shapes differ too (`__source_type`-tagged rows vs `{ row, typeName }`). Folding them into one walk would have to reconcile four different behaviours behind flags — that *moves* complexity rather than concentrating it (the deletion test fails), and the evaluator is partial-conformance, so a behaviour change surfaces as a wrong row. Same discipline as ADR 0007's comparator scope-out and ADR 0011's first-step-seed scope-out.
- Two table-name sites are left inline because they don't fit `linkTableName(qualifiedName, LinkDef)`: `engine.ts:4174` builds the name from a bare `linkName` *string* (no `LinkDef` in hand), and `engine.ts:11372` builds it from an already-resolved `sourceTable` that is not necessarily the storage owner — routing it through `linkTableName` would impose the owner walk and could change the table targeted. Different inputs, not this rule.

**Verification.** Behaviour-neutral: the backlink-heavy slice (`linkprops` / `linkatoms` / `group` / `select` / `for`, 713 tests) ran `177 failed / 533 passed / 3 skipped` **identically** before and after (the failures are the pre-existing partial-conformance baseline). 0 type errors. The substitution is byte-identical by construction.

**Consequences.** The storage decision and the junction-table name each have one home that the backlink read path now reads, instead of five inline copies apiece that could drift (the same hazard ADR 0010 closed for the compile/runtime link-owner walk). `linkTableName`'s sole definition is now the live pipeline's actual source for backlink junction tables.

**Why record it:** a future reader will see candidate #5 named "one backlink-resolution walk" and find the two functions still separate, with the consolidation landing on the *storage-dispatch* instead. That is intentional — the dispatch is the genuine, byte-identical duplication (and had an existing home the live pipeline ignored); the two walks are legitimately different traversals whose merge would move complexity, not concentrate it. The `4174`/`11372` table-name sites are left with reason (different inputs), so they aren't re-flagged as missed.

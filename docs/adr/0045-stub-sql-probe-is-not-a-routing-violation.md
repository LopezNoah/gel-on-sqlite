# The stub-SQL / runtime-probe is not a routing-authority violation (false positive)

A round-7 review candidate ("Make the strategy classifier the real authority") claimed that, although `docs/adr/0004` made `classifyExecutionStrategy` the single routing authority, the engine still *re-decides* routing at run time: it compiles a synthetic statement to (possibly stub) SQL, tries the Runtime evaluator first, and falls through to the SQL — the implication being a pervasive ADR-0004 violation around `engine.ts`'s "emits stub SQL that returns a single NULL row" path.

**Finding: false positive.** The premise does not survive reading the dispatch:

- The **main statement dispatch** (`executeQueryWithTraceImpl`) routes INSERT/UPDATE/DELETE → `runWriteWithAccessPolicies`, `group` → reject, and everything else (SELECT / select_expr / select_free / FOR) → `runGelSelectSQL`. It consults `classifyExecutionStrategy` only for the `reject` decisions (`select_free` / top-level GROUP that don't lower). It never probes the evaluator.
- The Runtime evaluator (`tryRuntimeSelectExprEvaluationAst`, now `runSelectExprEvaluation` — `docs/adr/0044`) has **exactly one caller**: the `select_expr`-body branch of `executeForLoop`. There, the runtime-vs-SQL decision is made by `selectExprNeedsRuntime` — the same predicate `classifyExecutionStrategy` is built on (`docs/adr/0004`) — which the evaluator consults on its first line and returns `undefined` when SQL should own the body. So the authority *is* the thing deciding; the engine is not re-deciding.
- The "stub SQL that returns a NULL row" is a compile-path artifact for FOR bodies that can't lower (UDF calls, link-property subqueries). The engine **never executes it**: when the body needs the runtime, the evaluator's result is used; when it doesn't, the evaluator returns `undefined` and the *complete* lowered SQL runs. There is no path on which the NULL-row stub reaches the result.

**Decision: not actioned.** The single probe site is correct and localized, and it carries a real nuance — a FOR over GROUP rows lowers fully to SQL and must prefer the SQL artifact over the evaluator (`iteratesGroupRows && sqlIsComplete`). Rewriting the implicit "try evaluator, `undefined` ⇒ fall through" into an explicit `selectExprNeedsRuntime` / `classifyExecutionStrategy` call would be **behaviour-identical** (the evaluator already gates on that predicate), at non-trivial risk on the well-tested FOR path, for a marginal readability gain. Not worth it.

**Why record it:** so a future review does not re-flag the stub-SQL-then-probe as an ADR-0004 violation. It isn't one — routing authority is centralized in `selectExprNeedsRuntime`/`classifyExecutionStrategy`, the main dispatch consults it, the one FOR-body probe delegates to it, and the stub SQL is compiled-but-never-run. The report over-read a localized implementation detail as an architectural breach (the same "candidates over-claim cleanness" pattern as `docs/adr/0040`/`0041`).

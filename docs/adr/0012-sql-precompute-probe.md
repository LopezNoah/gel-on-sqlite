# An optimistic SQL-probe seam (stop swallowing engine defects)

The round-3 review's candidate #3 flagged that the engine "tries to run a statement as SQL, and on any failure falls back to the runtime evaluator" via bare `catch { return undefined }` blocks that swallow **everything** — including a `TypeError` or other defect in a lowering path, which then surfaces as a wrong row instead of a thrown bug. Investigation narrowed the genuine instances of *this* pattern to two near-identical sites in `runtime/engine.ts`: `evaluateGlobalExpr` (computed-global defaults) and `evaluateForScalarIteratorViaSql` (FOR scalar iterators). Both did `compile → lowersToSingleSql gate → runGelSelectSQL → map`, wrapped in `catch { return undefined }`. (The review's wider "9 sites" count conflated these with JSON-decode catches — candidate #5 — parse-retries, and eval-fallbacks-to-`[]`, which are different patterns and out of scope here.)

**Decision (done):** Add `tryProbe(fn)` to `src/errors.ts` — optimistic-probe sugar over the existing `tryResult`: returns `fn()`'s value, or `undefined` when it fails as a **query problem** (`isQueryFailure`: E_SYNTAX / E_SEMANTIC / E_VALIDATION / E_UNSUPPORTED). Engine defects (`TypeError`, …) and non-query AppErrors (E_RUNTIME / E_SQL) **propagate** instead of being swallowed. Extract the duplicated probe body into one `tryRunSingleSqlRows(db, schema, stmtAst, context, compileContext?)` in `engine.ts` — "compile; if it lowers to a single SQL statement, run it and return the rows, else `undefined`" — built on `tryProbe`. The two sites now call it; each keeps only its own result-shaping (first-scalar vs mapped-array). One home for the SQL-precompute probe; the swallow rule is `isQueryFailure`, not catch-all.

**Decision (scoped out, deliberately):**
- The **raw-SQLite-column probe** in `evaluateForScalarIteratorViaSql`'s sibling path (`db.prepare(...).all()` guarded by `catch { return undefined }`) is left as-is: a missing-column `SqliteError` there is an *expected* "this type lacks that column, fall back" signal, not a defect, so swallowing is load-bearing and it is not an AppError-classified failure.
- The **JSON-decode catches** (`materializeGelSQLRows`, `normalizeGelSQLValue`, stored-value parsing) are candidate #5's concern (the row codec), not this one.
- **parse-retry** (`parseDefaultExprAst`) and **eval-fallback-to-`[]`** catches are different idioms and unchanged.

**Verification.** Behaviour-neutral on the suite: the probe-exercising slice (`for` / `functions` / `expressions` / `select`, 1198 tests) ran `480 failed / 715 passed / 3 skipped` both before and after — the failures are the pre-existing partial-conformance baseline; zero new failures. Critically, the *tightening* (rethrowing defects/non-query errors that the old `catch` swallowed) introduced **no** regression, which means no test was relying on a swallowed engine bug at these two sites — so it is a pure bug-surfacing improvement, not a risk taken. 0 type errors. 4 new unit tests (`tests/try_probe.test.ts`) pin `tryProbe`'s contract: value on success, `undefined` on query failure, **rethrow** on `TypeError` and on E_RUNTIME/E_SQL.

**Consequences.** A defect in the global-default or FOR-iterator SQL precompute path now throws (localised to the bug) instead of silently degrading to the runtime evaluator with a possibly-wrong answer. The probe rule has one home (`tryRunSingleSqlRows` + `tryProbe`), consistent with the `tryResult`/`isQueryFailure` taxonomy already in `errors.ts`.

**Why record it:** a future reader will see `tryProbe` used at only two sites and may try to "finish the job" by routing every `catch { return undefined }` through it. Most of the others swallow on purpose (raw-SQLite missing-column probes, JSON-decode fallbacks, parse retries) where the swallowed error is expected, not a defect — those are scoped out here with reason. The two routed sites are the ones where catch-all genuinely hid engine bugs.

# The two tokenizers share no extractable leaf (different representations, not duplication)

The round-4 review's candidate #7 (rated Speculative) proposed extracting a shared character-classification / literal-scanning / position-tracking leaf from `edgeql/tokenizer.ts` and `schema/schema_tokenizer.ts` — `CC_*` constants, `isAlphaCC`/`isDigitCC`/`isIdentPartCC`, `scanEscapeValue`/`readHexDigits`, `lineStarts`/`offsetToLineCol` — claimed "identically redeclared in both files." Inspection refutes the claim: the two tokenizers are written in **different representations**, not duplicated. There is no byte-identical (or even same-shaped) leaf to extract.

**They classify characters in incompatible ways.**

- `edgeql/tokenizer.ts` is a **charCode hot-path scanner**: 47 `CC_*` integer constants, `isAlphaCC(cc: number)` / `isDigitCC(cc: number)` / `isIdentPartCC(cc: number)` doing numeric range checks, 58 `charCodeAt` call sites, a precomputed `lineStarts` table with binary-search `offsetToLineCol`, and `scanEscapeValue`/`readHexDigits` operating on char codes. Zero regexes. It is a free-function scanner deliberately tuned for the EdgeQL expression language's hot path.
- `schema_tokenizer.ts` is a **class-based regex scanner**: 0 `CC_*` constants, 0 `charCodeAt`; character classification is `isIdentifierStart(ch: string) { return /[A-Za-z_]/.test(ch) }`, `isDigit(ch) { return /[0-9]/.test(ch) }`, `/\s/.test(ch)` (5 regex tests); escapes are handled inline in `readString()` via `if (ch === "\\")` string comparison; 725 `this.`/`private` references. It operates on single-character strings.

`isAlphaCC(cc: number)` (numeric range) and `isIdentifierStart(ch: string)` (regex on a string) are not the same function in different files — they take different types, use different mechanisms, and live in different module shapes (free function vs class method). Same for digit classification, escape scanning, and position tracking (`schema_tokenizer` has no `lineStarts`/`offsetToLineCol` at all — it tracks `this.line`/`this.column` incrementally).

**Why extraction is wrong, not just unnecessary.** A shared leaf would have to pick one representation, forcing a rewrite of the other tokenizer. Converting the EdgeQL tokenizer's charCode hot path to regex-on-strings would regress its performance and risk subtle behaviour change on a 1,246-line scanner that the whole query path depends on; converting the schema tokenizer to char codes is churn on a separate front end for no gain. ADR 0005 already records that the two are deliberately separate grammars (SDL declaration syntax vs the EdgeQL expression language) that intentionally do not share a tokenizer — this ADR adds that their *implementations* are also different in kind, so there is not even a mechanical leaf beneath the grammar boundary.

**Decision:** leave both tokenizers as-is. No code change. Record the decision so a future review does not re-propose the leaf.

**Why record it:** a future reader (or review) will see "is this a letter / a digit / whitespace" logic in both tokenizers and assume an extractable shared leaf, exactly as round-4's candidate #7 did. The logic is genuinely duplicated only at the *conceptual* level — the implementations use incompatible representations (charCode range checks vs string regexes, free functions vs class methods, precomputed `lineStarts` vs incremental position). Unifying them would force a representation rewrite of a hot-path scanner, not a mechanical extraction. ADR 0005 protects the grammar separation; this protects against re-litigating the implementation separation.

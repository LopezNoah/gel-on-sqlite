# The two `parseComputedExpr` functions stay separate (a false-positive duplication)

The round-4 review's candidate #6 proposed extracting the `parseComputedPropertyExpr` / `parseComputedLinkExpr` pair — present in both `schema/sdl_adapter.ts` and `schema/gel_persistence.ts` — into one shared `computed_expr_parsing.ts`, on the premise they are "identical intent, different entry points (string vs JSON pre-decode)." Closer inspection refutes the premise: they are genuinely different parsers for different input languages that merely share a name and return type — the same situation ADR 0009 recorded for the three `normalizeTypeName` variants.

**They are not the same function.**

- `sdl_adapter.ts` parses **arbitrary user-written SDL** (`exprText` from a declaration). `parseComputedPropertyExpr` there handles `sum(.link.field)` and `count(.link)` aggregates, `++` concat parts, scalar **and cast** literals, set literals, `.field` refs, `name(args)` calls with parsed arguments, and — as a catch-all — a **full `parseEdgeQL` fallback** that stores the raw text as an `edgeql_expr` for the IR compiler. It depends on ~10 SDL helpers (`stripOuterParens`, `detectCountOfLink`, `splitComputedConcatParts`, `parseScalarLiteral`, `parseCastScalarLiteral`, …) plus the EdgeQL parser. `parseComputedLinkExpr` similarly handles select-type exprs, `[is T]` backlinks, `select … filter … order by … limit …`, etc. via regexes.
- `gel_persistence.ts` parses **the output of its own `serializeComputedExpr`** (`meta.computed_expr`) — a closed serialize↔parse round-trip over a narrow canonical form. Its `parseComputedPropertyExpr` handles only `sum(.link.field)`, set literals, a crude `.startsWith(".")` field/function heuristic, and a raw-string `literal` fallback; its `parseComputedLinkExpr` handles only `.<link[is T]` and `.link` via string splits. No count detection, no concat, no cast, no `edgeql_expr` fallback, no EdgeQL parser.

**Why merging is wrong, not just unnecessary.** The persistence parser is the inverse of `serializeComputedExpr`; the two must stay paired, and its input is never arbitrary SDL — only what the serializer wrote. Replacing it with the SDL parser would (1) couple the persistence round-trip to the SDL front-end (`parseEdgeQL` + the SDL helper web), and (2) change behaviour — the SDL parser's different heuristics (e.g. the curated regex/`edgeql_expr` paths) would interpret the serialized canonical strings differently from the crude round-trip parser. That is a behaviour-affecting change, not the byte-identical consolidation the candidate assumed.

**The genuinely-shared piece is already extracted.** The one rule both parsers legitimately share — set-literal parsing — already lives in `schema/computed_expr.ts` as `parseComputedSetLiteralExpr`, imported by both. The factoring that was warranted has already happened; what remains are two domain-specific parsers.

**Decision:** leave the two parsers separate. No code change. Record the decision so a future review does not re-suggest the merge.

**Why record it:** a future reader (or review) will see two same-named `parseComputedPropertyExpr` / `parseComputedLinkExpr` functions and assume leftover duplication, exactly as round-4's candidate #6 did. They are deliberately separate — an SDL-source parser vs a serializer round-trip parser, like the `normalizeTypeName` variants of ADR 0009 — and the shared rule (`parseComputedSetLiteralExpr`) is already in `computed_expr.ts`. Merging them would couple persistence to the SDL front-end and change behaviour.
